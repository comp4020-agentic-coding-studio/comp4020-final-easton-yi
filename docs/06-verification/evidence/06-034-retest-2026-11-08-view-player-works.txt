== Why (call order, order.spec.ts outside the repository)
  motion=no-preference: calls scrollIntoView(exhibits-h) then scrollTo([0, 0]); scrollY per frame: all [0] over 90 frames
  motion=reduce: calls scrollIntoView(exhibits-h) then scrollTo([0, 0]); scrollY per frame: all [0] over 60 frames
The link's handler (src/client/world/WorldStage.tsx, 'View player works') calls scrollIntoView on #exhibits-h; the
same click then reaches the app's router handler (src/client/router.ts onLinkClick -> navigate), which pushes
/#exhibits-h and calls window.scrollTo(0, 0). Both happen in the same millisecond. Headless Chromium applies the
later call, so the page stays at the top. A browser that lets the earlier smooth scroll continue would end at the
exhibition, which would be consistent with the author's observation; that is an explanation, not a tested fact.
With reduced motion both scrolls are instant, so the later scrollTo(0, 0) is expected to win in any browser; this
is inferred from the code and the headless result, not tested in a real browser.

== Fix and retest, appended 2026-11-08 (everything above is unchanged)
Authorised narrowly scoped behaviour correction. One owner for the scroll: the app router.
  src/client/router.ts navigate(): for a hash on the current page (same path and query) it scrolls the target into
    view (smooth, or instant with prefers-reduced-motion) instead of window.scrollTo(0, 0); any other in-app
    navigation still starts the new page at the top; a link to the URL that is already current replaces the history
    entry instead of adding a duplicate (as a native anchor does); a malformed hash escape falls back to the top.
  src/client/world/WorldStage.tsx: the desktop link and the touch Menu's link no longer prevent the navigation or
    scroll by themselves (the touch one used to defer a frame); they only leave fullscreen (home) or remember the
