Retest 2026-11-07 — spec/versions.test.ts rate-limit instability (docs/90-reference/90-01-implementation-status.md, Known limitations)
Environment: local, WSL2, Node v24.21.0, production build with ENABLE_TEST_HOOKS=1, fresh DATA_DIR per server, one server per batch of 10 repeats.
Code: base fa23e6a plus the uncommitted working tree (identity in 06-020).

Cause (inspected, not reproduced): the versions spec's shared 'Owner' account draws on one per-user command bucket
(src/server/core/coordinator.ts execute(), TokenBucket keyed by actor.userId; TRANSPORT.commandsPerSecond 2, commandBurst 4).
The versions spec's tests run back to back on that account; a replay of the server's own command log through the bucket
arithmetic (scripts/bucket_margin.py, outside the repository) shows the shared Owner reaching as low as 1.02 tokens before a
take on the unchanged spec: one token from a RATE_LIMITED rejection. The 2026-10-06 failures (3 of 9 runs) were that
rejection. The failure did not reproduce on this machine in 10 repeats before the change, so it is explained, not reproduced.

Change (spec/versions.test.ts only; no server, limit or middleware change; no retries; no assertion removed):
  - beforeEach waits until ceil(commandBurst / commandsPerSecond) = 2 s have passed since the previous test ended, so each
    test starts with a full bucket. The constants are read from src/shared/config.ts, not copied.
  - a separate test, 'command rate limit', registers its own account and sends commandBurst + 1 snapshot.create commands:
    the first commandBurst are accepted, exactly one is RATE_LIMITED with 0 < retryAfterMs <= ceil(1000 / rate), no version
    is created by the refused one, and a command after the refill is accepted. Signups stay within the spec budget (40).
